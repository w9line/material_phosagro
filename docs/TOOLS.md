# Инструменты AI-ассистента контроля сырья

Актуальный реестр на **13 августа 2026**: **11 инструментов**.

Единый источник описаний и схем: `services/api/core.py → TOOL_REGISTRY`.
Список для внешнего агента: `GET /api/v1/agent/tools`.

Все инструменты read-only: они считают и возвращают результат, но сами не списывают остатки и не изменяют производственные данные. Подтверждение плана выполняется отдельным авторизованным API-методом.

## Общие правила

- `raw_mass_kg` — физическая масса сырья.
- `active_mass_kg` — масса активного вещества; эти величины не смешиваются.
- Потребность для планов и дефицита указывается в `kg_active`.
- `GOOD`, `REWORK`, `REJECTED` вычисляются по правилам материала.
- `REJECTED` никогда не попадает в план.
- `REWORK` учитывается только при `allow_rework=true` / `include_rework=true`.
- Расчёты содержат `meta.data_version`, время расчёта, параметры и единицы измерения.
- При нехватке обязательных вводных агент не запускает тул, а задаёт вопрос или показывает встроенную форму.

## Справочник тулов

### 1. `check_batch_quality` — Качество партии

Проверяет одну партию по действующим порогам качества.

**Вход:**

- `batch_id: string` — обязательный идентификатор партии.

**Возвращает:** исходные поля партии, статус `GOOD` / `REWORK` / `REJECTED`, коэффициент восстановления, причину классификации, теоретическую и доступную массу активного вещества.

**Примеры:**

- «Проверь качество партии A-001»
- «Какой статус у B-002?»

Если `batch_id` не указан, агент предлагает выбрать партию из реестра.

### 2. `get_batch_details` — Детали партии

Показывает фактическую карточку партии без отдельного действия над данными.

**Вход:**

- `batch_id: string` — обязательный идентификатор.

**Возвращает:** материал, массу сырья, остаток, концентрацию, дату поступления, поставщика, склад, сертификат, статус и расчёт активного вещества.

**Примеры:**

- «Покажи детали партии C-001»
- «Открой карточку A-004»

### 3. `get_oldest_batches` — Самые старые партии

Находит партии с самой ранней датой поступления.

**Вход:**

- `material_type: string | null` — необязательный фильтр материала.
- `limit: integer` — необязательный лимит, от 1 до 20; по умолчанию 5.

**Возвращает:** список партий, отсортированный по `arrival_date`, затем по времени создания и `batch_id`.

**Примеры:**

- «Какие самые старые партии?»
- «Покажи три самые старые партии материала B»

### 4. `build_chart` — График

Строит график по данным реестра, качеству, браку, плану или сценарию. График отрисовывается в чате, открывается в модальном окне и скачивается в SVG.

**Основные входные параметры:**

- `chart_type`: `inventory`, `quality`, `material_quality`, `concentration`, `metric`.
- `metric`: любая доступная метрика из списка ниже.
- `group_by`: `material`, `status`, `batch`, `arrival_date`, `policy`.
- `material_type`: необязательный фильтр.
- `requirements`, `policy`, `policies`, `changes_percent` — используются для графиков плана и сценария.

**Доступные метрики:**

| Метрика | Что показывает | Единица |
| --- | --- | --- |
| `raw_mass` | Сырьё | `kg_raw` |
| `active_mass` | Доступное активное вещество | `kg_active` |
| `theoretical_active_mass` | Теоретическое активное вещество | `kg_active` |
| `recovery_loss` | Потери восстановления | `kg_active` |
| `concentration` | Концентрация | `%` |
| `batch_count` | Количество партий | партии |
| `status_count` | Количество партий по качеству | партии |
| `status_share` | Доля партий по качеству | `%` |
| `age_days` | Возраст партии | дни |
| `rejection_batch_count` | Проблемные партии | партии |
| `rejection_raw_mass` | Брак и доработка по сырой массе | `kg_raw` |
| `rejection_active_mass` | Брак и доработка по активному веществу | `kg_active` |
| `rejection_share` | Доля брака и доработки | `%` |
| `required_active_mass` | Требуемое активное вещество | `kg_active` |
| `plan_available_active_mass` | Доступное для плана активное вещество | `kg_active` |
| `planned_batch_count` | Выбранные планом партии | партии |
| `covered_active_mass` | Покрытая потребность | `kg_active` |
| `deficit_active_mass` | Дефицит | `kg_active` |
| `coverage_percent` | Покрытие потребности | `%` |
| `raw_mass_used` | Использованное сырьё | `kg_raw` |
| `loss` | Потери плана | `kg_raw` |
| `safe_growth_percent` | Безопасный рост потребности | `%` |
| `deficit_delta` | Изменение дефицита | `kg_active` |
| `base_deficit_active_mass` | Базовый дефицит сценария | `kg_active` |
| `new_deficit_active_mass` | Новый дефицит сценария | `kg_active` |
| `base_rework_batch_count` | REWORK-партии в базе | партии |
| `new_rework_batch_count` | REWORK-партии после сценария | партии |

**Примеры:**

- «Построй график остатков»
- «Сделай график количества каждого материала и его качества»
- «Покажи долю брака по материалам»
- «Сравни покрытие по стратегиям на графике»

### 5. `classify_batches` — Классификация

Повторно рассчитывает статусы партий по текущим правилам качества.

**Вход:**

- `material_type: string | null` — необязательный фильтр.
- `only_unclassified: boolean` — параметр схемы для режима непроверенных партий.

**Возвращает:** `checked`, количество `GOOD`, `REWORK`, `REJECTED` и метаданные расчёта.

**Примеры:**

- «Классифицируй все партии»
- «Пересчитай классификацию для A»

### 6. `get_inventory_summary` — Остатки

Сводит остатки сырья и активного вещества по материалу и статусу.

**Вход:**

- `material_type: string | null` — необязательный фильтр.
- `group_by: material_and_status` — текущая группировка по материалу и качеству.

**Возвращает по группам и в итогах:**

- число партий;
- `raw_mass_kg`;
- теоретическое активное вещество;
- доступное активное вещество;
- потери восстановления;
- средние значения на партию.

**Примеры:**

- «Покажи остатки»
- «Какие остатки по A?»
- «Сколько активного вещества в среднем у материала B?»

### 7. `build_weekly_plan` — Недельный план

Строит preview производственного плана без изменения остатков.

**Вход:**

- `requirements: object` — потребность по материалам в `kg_active`.
- `policy`: `strict_fifo`, `hybrid` или `max_concentration`.
- `allow_rework: boolean` — разрешить использование REWORK.

**Логика базовой производственной стратегии `hybrid`:**

```text
GOOD по FIFO → REWORK по убыванию концентрации → дефицит
```

**Возвращает по каждому материалу:** потребность, доступный запас, покрытие, процент покрытия, дефицит, выбранные партии, использованную массу сырья, потери и объяснение выбора.

**Примеры:**

- «Построй недельный план: A 3000, B 2500, C 1800 кг активного вещества»
- «Сделай план по strict FIFO»

Preview можно подтвердить отдельно. При подтверждении проверяются владелец плана, `data_version`, остатки и транзакционность операции.

### 8. `check_material_deficit` — Дефицит

Сравнивает потребность с доступным активным веществом.

**Вход:**

- `requirements: object` — обязательная потребность в `kg_active`.
- `include_rework: boolean` — учитывать ли REWORK.

**Возвращает:** покрытие, доступный актив, выбранные партии и `deficit_active_mass_kg` по каждому материалу.

**Примеры:**

- «Проверь дефицит A 3000 кг активного вещества»
- «Хватит ли сырья на A 3000, B 2500 и C 1800?»

Без требований агент не запускает расчёт, а просит указать потребность.

### 9. `compare_allocation_policies` — Сравнение стратегий

Сравнивает несколько политик распределения на одной и той же потребности.

**Вход:**

- `requirements: object` — потребность в `kg_active`.
- `policies: array` — одна или несколько политик: `strict_fifo`, `hybrid`, `max_concentration`.

**Стратегии:**

- `strict_fifo` — ранние партии по FIFO.
- `hybrid` — GOOD FIFO, затем REWORK по концентрации.
- `max_concentration` — сначала партии с максимальной концентрацией.

**Возвращает:** отдельный полный preview-план для каждой стратегии, включая покрытие, дефицит, сырьё, потери, партии и причины выбора.

**Примеры:**

- «Сравни стратегии FIFO, Hybrid и Max concentration для A 3000, B 2500, C 1800»
- «Что выгоднее по сырью: FIFO или максимальная концентрация?»

### 10. `generate_rejection_report` — Отчёт по браку

Формирует read-only отчёт по проблемным партиям.

**Вход:**

- `material_type: string | null` — необязательный фильтр.
- `include_rework: boolean` — включать REWORK.
- `include_rejected: boolean` — включать REJECTED.

**Возвращает:** `report_id`, список партий, общее количество и общую оставшуюся массу сырья к решению.

В интерфейсе отчёт можно открыть отдельной страницей и скачать в CSV.

**Примеры:**

- «Создай отчёт по браку A»
- «Покажи проблемные партии по всем материалам»

### 11. `simulate_requirement_change` — Сценарий потребности

Сравнивает базовый и изменённый спрос, не изменяя склад.

**Вход:**

- `base_requirements: object` — базовая потребность; если не передана, используются сохранённые требования.
- `changes_percent: object` — изменение по материалам, например `{ "A": 10, "B": -5 }`.
- `policy`: `strict_fifo`, `hybrid` или `max_concentration`.

**Возвращает:** базовый план, новый план, новые требования и сравнение по каждому материалу:

- базовый дефицит;
- новый дефицит;
- изменение дефицита;
- число REWORK-партий до и после;
- безопасный рост потребности.

**Примеры:**

- «Что будет, если B вырастет на 20%?»
- «Смоделируй A +10% и C -5% по hybrid»

## Составные сценарии

Агент умеет выполнять безопасные цепочки тулов в заданном порядке:

| Запрос | Последовательность |
| --- | --- |
| Остатки и график | `get_inventory_summary → build_chart` |
| Отчёт по браку и график | `generate_rejection_report → build_chart` |
| Классификация и отчёт по браку | `classify_batches → generate_rejection_report` |
| Качество и детали партии | `check_batch_quality → get_batch_details` |
| План и дефицит | `build_weekly_plan → check_material_deficit` |
| План и сравнение стратегий | `build_weekly_plan → compare_allocation_policies` |
| План и график | `build_weekly_plan → build_chart` |

Результаты цепочки объединяются в один ответ чата; отчёт или график получает отдельную кнопку для открытия.

## Как работает уточнение

Если параметров не хватает, `route_intent()` возвращает `CLARIFY`, а не запускает тул с пустыми аргументами.

- Качество/детали без `batch_id` → выбор партии.
- Остатки без материала → выбор материала или «все материалы».
- Дефицит без `requirements` → запрос потребности.
- Недельный план без стратегии → выбор стратегии, затем поля по каждому материалу.
- Сравнение стратегий без потребности → встроенные поля A/B/C и кнопка запуска.
- Сценарий без процентов → поля процентов и выбор политики.
- График без достаточного контекста → уточнение метрики, группировки или параметров плана.

## Важное различие: тул и API-операция

В проекте есть операции, которые не являются агентскими тулами, но используют их расчёты:

- `POST /api/v1/plans/preview` — создаёт preview и сохраняет владельца/версию данных.
- `POST /api/v1/plans/{plan_id}/confirm` — отдельное подтверждение, списывает остатки транзакционно.
- `POST /api/v1/plans/production/download` — экспортирует именно производственный недельный план в CSV по базовой стратегии.
- `POST /api/v1/imports/preview` и `/commit` — проверка и импорт данных.
- `POST /api/v1/generator/generate` — генерация синтетического набора; это отдельный сервис данных, не тул агента.

## Контракт внешнего агентского пакета

Папка `agent-package/` использует те же 11 имён тулов и не знает структуру базы данных. Backend подключается через gateway:

```http
POST {BACKEND_URL}/internal/tools/{tool_name}
X-Agent-Token: {AGENT_SERVICE_TOKEN}
Content-Type: application/json
```

Внешний агент может работать через:

```http
POST /v1/chat
POST /v1/chat/stream
```

Потоковый ответ использует SSE-события `status`, `clarify`, `tool`, `token`, `done`, `error`.

- Проверки тулов и цепочек: `services/api/tests/test_scenarios.py`, `test_agent_safety.py`, `test_router_30.py`, `test_robustness.py`.
